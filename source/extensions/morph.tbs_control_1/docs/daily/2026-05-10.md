## 문제/증상 (정리)

1. **EP1/EP2 깜빡임**: 동일한 `foup_progress_label` 한 줄에 EP1 진행 텍스트 → EP2 진행 텍스트가 번갈아 덮어써져 시각적으로 ‘깜빡인다’.
2. **단일 EP 내부에서도 텍스트 폭주**: `_run_ep_foup_process` 가 1 회 공정에 `_wait_with_progress` 를 3 번 호출(+Y 1s / 공정 30~60s / -Y 1s). 각 단계가 자체 0% → 100% 사이클이라 단일 EP 안에서도 텍스트가 자주 급변.
3. **종료 후 잔상**: -Y 단계가 끝나도 라벨이 마지막 텍스트로 그대로 남아 있어, 다음 emit 전까지 “진행 중처럼” 보이는 잔상 문제.

---

## 원인 분석

- (1) UI 측 위젯이 “채널당 1개” 라 EP/단계 정보가 같은 자리에 덮어써짐 → 깜빡임의 본질 원인.
- (2) 엔진은 한 번에 1건만 진행(`simpy.Resource(capacity=1)`)이어도, 단계 전환과 EP 교대가 빠르게 일어나면 동일 라벨 텍스트가 통째로 바뀌어 “번갈아 보임” 으로 인식됨.
- (3) DONE 도착 후 라벨을 idle 로 되돌리는 콜백이 없어 잔상.

---

## 최종 해결

- **EP 별 라벨 분리**: 각 EP 가 자기 줄만 갱신 → 다른 EP/단계 텍스트가 같은 자리에 덮어쓰는 일 자체가 사라짐.
- **payload `port_id` 라우팅**: engine ↔ UI 컨트랙트로 `port_id` 한 키만 추가. UI 는 정규식 폴백 없이 정확히 라우팅 가능. 폴백 경로(label/detail 의 `EPn` 정규식)도 함께 두어 호환성 유지.
- **자동 idle 복귀**: -Y DONE 시 1.05초 뒤 해당 라벨만 “대기” 로 되돌려 잔상 제거. 다른 EP 라벨은 무관 → 깜빡임 없음.
- **Stop/Reset 안전망**: 보류된 1회성 sub unsubscribe + `_reset_all_foup_labels(ext)` 로 일괄 idle 화.

## 신설/수정된 함수

- `simulation_engine.TBSSimulationEngine._wait_with_progress(... port_hint: str = "")`
  - payload 에 `"port_id": port_hint` 항상 포함.
- `control_window._foup_label_idle_text(screen_num, ep_id)`
  - 라벨 idle 텍스트를 한 곳에서 생성(생성/리셋 일관성).
- `control_window._reset_foup_label_now(ext, screen_idx, ep_id)`
  - 해당 화면/EP 라벨 한 줄을 즉시 idle 표시로 복귀.
- `control_window._reset_all_foup_labels(ext)`
  - 모든 화면/EP 라벨 일괄 idle 화(Reset/Stop 안전망용).
- `control_window._schedule_foup_label_reset(ext, screen_idx, ep_id, delay_sec=1.05)`
  - 1회성 update event subscription 으로 `delay_sec` 후 해당 라벨만 idle 화.
- `control_window._update_sim_progress`
  - FOUP_PROCESS 분기를 EP 라벨 dict 라우팅 + 단계 색 구분 + DONE 자동 reset 로직으로 교체.
- `control_window._create_sim_monitor_channel_column`
  - `foup_progress_labels: dict[str, ui.Label]` 생성(EP1/EP2/EP3) + `progress_frame.height = 270`.
- `control_window.on_sim_stop_clicked`
  - 보류된 `_foup_label_reset_subs` unsubscribe + `_reset_all_foup_labels(ext)` 호출 추가.

## Phase 6 — REQ-011 LAM Sequence Editor 가 TBS 와 동일한 4 종 step (오후)

### 사용자 요청

> "시퀀스 편집기에서는 tbs 시퀀스 편집기와 동일하게 usd 타임라인 뿐 아니라 rotate, move, delay 등등 동일하게 스탭형식으로 추가가 되어야 한다. 단지 타임라인에서 인스턴스선택부분만 제외하고 모든것이 동일하게 동작하도록 하고 json 도 마찬가지로 스탭으로 생성하고 json 으로부터 스탭을 생성하기도 해야 한다."

### 결정값

- LAM Sequence Editor 의 step 종류 = TBS 와 동일 4 종(`USD_TIMELINE / MOVE / ROTATE / DELAY`).
- 각 종별 UI 행의 필드·기본값·JSON schema 모두 TBS 와 동일.
- 차이점은 **USD_TIMELINE step 한 곳에만** — UI 맨 위에 LAM 인스턴스 드롭다운/상태 배지/Re-bind. 선택한 인스턴스 정보가 step["ref"] 4-tuple 로 박힌다(REQ-006).
- JSON Save/Load 도 TBS 와 동일 schema. 모르는 키는 무시하고 알려진 키만 복원.

### 핫픽스 3 — Run 즉시 영구 freeze (background thread USD write × main thread USD lock cross-wait)

- 사용자 보고: 핫픽스 2(import lock 정리) 적용 후에도 MOVE step 추가 후 Run 즉시 영구 freeze.
- 진단 로그(diagnostic print 6 곳): 사용자 콘솔 마지막 줄이 `[LAM/MOVE] BEFORE _get_prim_local_translate prim=/World/aaa` 로 끝나고 `AFTER _get_prim_local_translate` 가 안 찍힘 → 정확한 deadlock 지점은 `_get_prim_local_translate` 안의 `_get_or_create_offset_translate_op` 의 `x.AddTranslateOp(opSuffix="TBS_OFFSET")` (= **첫 MOVE 라 TBS_OFFSET op 가 없어서 background thread 가 처음 author 시도**).
- 원인: 사용자의 USD(`N_07_Laser_Cutting111.usd`) 는 외부 https 텍스처를 참조하는 무거운 자산이라, USD 로드 직후 main thread 가 MDL 컴파일 + RTX 텍스처 fetch 로 **stage write lock + Sdf change notification dispatch lock** 을 장시간 점유. 그 와중에 background thread (`LamSequenceRunner.run()`) 에서 `AddTranslateOp` 가 같은 lock 을 대기 → 영구 deadlock.
- TBS 가 작동하는 이유: TBS 는 USD load 직후 baseline 단계에서 **main thread 가 미리** 모든 TBS_OFFSET op 를 author 해 둠. sequence run 중 background thread 는 read 만 하면 충분(write 는 `_on_update` = main thread).
- 해결: LAM 의 USD write 경로를 **main thread 의 다음 update tick 으로 dispatch**(fire-and-forget). background thread 는 dispatch 만 하고 step duration 만큼 sleep → 다음 step 진행. main thread 의 update 콜백 안에서 USD write 가 일어나므로 stage lock 충돌 없음.
- 신규 헬퍼: `lam_sequence_engine._dispatch_main(fn)` — 다음 update tick 에 1회 subscribe 후 fn() 실행 → unsubscribe.
- 적용 범위:
  - `_start_move` — `stop_prim_translate_animation` + `run_prim_translate_animation` 전체를 `_dispatch_main` 으로 감쌈. (사용자 freeze 지점 — 핵심 fix)
  - `_start_rotate` — 3 개 모드(simple/lock_world_center/world_pivot_euler) 의 USD write 호출을 모두 `_dispatch_main` 으로 감쌈. 충돌 stop 도 같이 main 에서.
  - `_start_step` 의 `hide_for_step` — 동일한 deadlock 위험이 있으나 default OFF 옵션이므로 우선 보류, 주석으로 마이그레이션 가이드 추가. 사용자가 `hide_enabled` 를 사용하기 시작하면 같은 패턴으로 마이그레이션.
  - `_start_usd_timeline` 의 `apply_world_space_offset_correction`, `_apply_start_snapshot` — 동일 위험, default OFF, 주석으로 보류.
- 진단 로그(daily/2026-05-10.md 의 진단 6 지점) 는 그대로 유지 — 차후 freeze 발생 시 정확한 지점 추적용.
- 영향: TBS 0 줄 변경. LAM lint 0 errors. background thread 의 sleep 동작은 그대로(=duration 정확). main thread 에 1 frame 정도 추가 update 콜백이 들어가지만 무시 가능.

## 핫픽스 4 — `USD_TIMELINE` 재생이 실제 화면에 보이지 않음 (`wrote=0`)

### 사용자 보고 로그(요약)

```
[LAM/SEQ] step[0] USD_TIMELINE ... range=frames[0.0,100.0] sp=1.0 loop=False ok=True est_duration=3.333s asset_time=[0.0,0.0]@30.0fps
```

- `wrote=0` + `fallback NO timeSamples` 가 동시에 발생 → 가설 A(자산 timeSamples 미발견) + 가설 B(reauthor 가 reference timeSamples 를 마스킹 못 함) 가 동시에 성립한다는 의미.

## 핫픽스 5 — 한 인스턴스만 trigger 했는데 다른 인스턴스도 같이 재생됨

## 핫픽스 6 — Per-Instance Layer Offset Mapping (진정한 independent playback)

### 사용자 보고 / 문제 정의

핫픽스 5 적용 후에도 여전히 **한 인스턴스만 trigger 했음에도 다른 인스턴스도 같이 재생**됨. 핫픽스 5 의 모델은 단일 활성 인스턴스 케이스만 다루는 단순 freeze (state 전환 시 `(0,1)` ↔ `(freeze_tc, 0)`) 였는데, 두 인스턴스가 모두 활성이 되는 경로(혹은 default `state="stopped"` 의 freeze 가 첫 trigger 전에 적용되지 않은 경로)에서 같이 재생되는 문제 재발.

### 정확한 진단 (사용자 요청 1~6)

1. **`omni.timeline.set_current_time()` 을 USD_TIMELINE 평가의 driver 로 쓰면** → 마지막 인스턴스의 vt 가 stage current time 을 덮어씀 → 모든 인스턴스가 같은 시각으로 평가 → independent playback 의 본질을 무너뜨림.
2. **reference 내부 timeSamples 가 root layer default 보다 강한 이유** — USD value resolution 의 옵션 강도 = layer 강도 × opinion 종류. cross-layer 에서 root 의 default 는 reference 의 timeSamples (valid range 안) 를 마스킹하지 못한다. root 에 timeSamples 를 author 하거나 attr.Block() 하지 않으면 안 됨.
3. **현재 reauthor 방식의 정체**:
   - **value resolution 문제** (핵심): root default 가 reference timeSamples 를 못 이김.
   - **weak layer authoring 문제** (부분): root 가 stronger 임에도 weak opinion type(default) 사용.
   - **UsdSkel evaluation** (사용자 자산이 SkelAnim 기반이면 매우 큼): SkelRoot 가 합성하는 결과 attribute 들이 `prim.GetAuthoredAttributes()` 로 잡히지 않음 → 캐시가 빈 채로 끝남(`cache built attrs=N=0`).
   - **Hydra evaluation**: SkelRoot 합성 결과를 그대로 받음 — root default 변경 무의미.
4. **"독립 runtime" + "global timeline" 동시 사용**: **완전한 논리 충돌**. virtual_time 모델의 출력을 다시 stage 의 단일 currentTime 으로 환원하면 vt 모델이 무력화됨. → 두 모델을 서로 다른 책임으로 분리: vt 는 evaluator 내부 추적용, 화면 평가는 reference 의 SdfLayerOffset 매핑이 담당.
5. **independent playback 의 실제 구현 수단**:
   - **per-reference `Sdf.LayerOffset` 매핑** ✅ — 정통, 가장 가벼움, 한 번 author 후 자동 sync.
   - stronger layer(session)에 timeSamples 매 frame author — 무거움, Skel 자산엔 무력.
   - sublayer ordering — 같은 한계.
   - value clip detachment — 자산이 안 쓰면 무관.
   - UsdSkel rebinding — Skel 자산일 때 부분적 보강.
   - pose baking — 매 frame 결과를 baked timeSamples 로 author. 가장 무거움 — 비현실적.
   → **per-reference SdfLayerOffset 매핑 채택**.
6. **현재 → 진정한 independent playback 으로 가려면**:
   - `_advance_stage_time` 의 인자: 인스턴스 vt → **wall clock master_seconds** 로 변경.
   - 핫픽스 5 의 단순 freeze (state 전환 시 0/1) → **per-instance offset 매핑** 으로 확장.
   - attribute reauthor 호출은 호환 보존만, 효과 없음 (그대로 둠).

### 모델 (핵심 수식)

```
master_tc = master_seconds * tps_master       (evaluator 의 자체 wall clock)
inst_tc(t) = layerOffset.offset + master_tc(t) * layerOffset.scale

playing 진입 시 한 번만 author:
  scale_i  = inst.speed
  offset_i = (inst.virtual_time*tps + asset_start_tc) - start_master_tc * inst.speed
  → 이후 master_tc 가 wall clock 으로 진행하면 inst_tc 가 inst.virtual_time*tps 와 자동 sync.

stopped/paused 진입 시:
  scale_i  = 0
  offset_i = 그 시점의 inst_tc (=freeze frame)
  → master_tc 진행과 무관하게 inst_tc 가 항상 같은 frame.
```

다중 활성 인스턴스 동시 재생: 각자 다른 `(offset, scale)` 이라 같은 `master_tc` 에서도 서로 다른 `inst_tc` 로 평가 = **진정한 independent playback**.

## 핫픽스 6.2 — Sdf 직접 조작 + master_seconds 누적 조건 + fps 30 고정

### 사용자 보고 (3 가지 문제 동시)

1. **여전히 두 USD 가 같이 재생됨**. 로그상 `aaa` 만 PLAY, `aaa_1` 은 FREEZE 인데 화면은 둘 다 진행.
2. **첫 RUN 시 갑자기 1000단위 frame 부터 재생**, 두 번째 RUN 부터 정상.
3. **fps 는 30 고정**.

### 진단

1. `refs_count=-1` → `Usd.References.GetAddedOrExplicitItems()` 가 exception (해당 메서드는 `Sdf.ReferencesProxy` 에만 존재). fallback 으로 새 reference 추가했지만 — `Usd.References.ClearReferences()` 는 EditTarget layer 의 prim spec 의 `prepended` 만 비울 뿐, `Open Master USD` 로 직접 load 한 케이스에서는 root layer (master.usd) 의 prim spec 에 이미 author 된 reference (explicit) 를 무효화하지 못함. → 두 reference 가 합성되어 freeze 효과 0.
2. evaluator 의 `_master_seconds` 는 `_on_update` 마다 `+= dt` 였음. 시작 후 RUN 까지 wall clock 이 44s (1342tc) 누적 → mapping author 시 `offset=-1342.440tc, scale=1.0` → reference 평가는 정상이지만 stage current time 슬라이더가 frame 1342 부터 표시 → 사용자에게 이상하게 보임. 두 번째 RUN 부터는 모두 stopped 시 reset 되어 0 부터 시작.
3. evaluator 가 `stage.GetTimeCodesPerSecond()` 를 사용. 사용자 master USD 가 다른 값(예: 1.0/24)이면 mapping 이 어긋남.

### 변경 — `morph.lam_control/morph/lam_control/lam_runtime_evaluator.py`

1. **`_set_prim_layer_offset` 를 `Sdf.PrimSpec.referenceList` 직접 조작으로 변경**:
   - root layer 의 prim spec 확보 (없으면 `Sdf.CreatePrimInLayer` 로 생성).

### 진단 — `Sdf.PrimSpec.referenceList` 직접 조작 방식의 구조적 한계

1. **Sdf 직접 조작이 Hydra ChangeNotice 를 보장하지 않는 경우 발생** — `Sdf.ListEditorProxy.SetItems()` 는 ChangeBlock 안에서 일어나야 압축 알림이 나간다. 그렇지 않으면 viewport cache 가 invalidate 안 되어 LayerOffset 이 적용되어도 시각적으로 안 변함.

3. **stage TPS 가 master USD 와 다른 경우 LayerOffset 의 freeze 가 비율 변환되어 무력화될 가능성** — `60→30` 변경 후 LayerOffset 을 30 기준으로 author 했는데 reference 평가 시 또 한 번 비율 변환이 일어남.

### 결정 — root layer 직접 조작 방식 폐기 + Opt-1 (per-instance anonymous sublayer) 즉시 전환

전환 사유:
- Opt-1 은 USD 의 reference resolution 의 cross-layer override 동작에 의존하지 않는다 — sublayer 자체가 stronger 이므로 무조건 winner.
- 사용자 master USD 가 절대 변경되지 않는다 (in-memory anonymous layer 만 추가).
- `Sdf.ChangeBlock` 으로 묶어 한 번의 ChangeNotice → Hydra cache 안전 invalidate.
- 인스턴스마다 자기 sublayer 1개 → mapping 변경 시 다른 인스턴스 sublayer 영향 0.

```
    └─ ...
```

USD 의 `subLayerPaths.insert(0, ...)` 는 **그 layer 의 sublayer 들끼리의 우선순위** 만 결정한다. **root layer 자체는 자기 sublayer 들보다 항상 strong**. 따라서 root.subLayerPaths 에 어떤 sublayer 를 끼워도 root layer (= master_1.usd) 보다 stronger 가 될 수 없다.

→ master_1.usd 의 reference (LayerOffset 없음 = identity) 가 winner, LAM sublayer 의 LayerOffset 은 weaker 라서 무시됨. 두 reference 가 같이 활성화되어 master USD 의 reference 만 평가됨 = freeze 안 됨.

### 결정 — session layer 의 sublayer 로 attach (Opt-2 정통)

session layer 는 root 보다 무조건 stronger. session layer 의 sublayer 들도 root 보다 strong. 인스턴스별 sublayer 를 session layer 의 `subLayerPaths.insert(0, ...)` 로 등록하면:

```
SessionLayer
    ├─ session sublayer[0] (lam_inst_aaa)    ← strongest, winner
    ├─ session sublayer[1] (lam_inst_aaa_1)  ← strongest, winner
RootLayer (master_1.usd)
    └─ ...
```

session layer 는 stage 와 함께 자동 폐기되므로 사용자 master USD 파일에 영향 0.

### 변경

#### 1. `morph.lam_control/morph/lam_control/lam_master_stage.py`

  - 1순위 `stage.GetSessionLayer()` (정상 케이스).

### 진단 — 두 가지 결정적 발견

#### 발견 A: `SdfLayerOffset(0, 0)` 은 USD invalid LayerOffset

USD 문서:
> An invalid offset has 0.0 scale. **Invalid offsets cannot be inverted, and can produce unspecified behavior when evaluated.**

`SdfLayerOffset.IsValid()` 는 `scale != 0` 만 True 를 반환한다. 일부 USD 빌드는 invalid LayerOffset 을 자동으로 identity `(0, 1)` 로 fallback 처리하여, 우리가 의도한 freeze 가 시각적으로는 적용되지 않고 자산 timeSamples 가 그대로 평가된다 → 같이 재생됨.

#### 발견 B: TOP WINNER 진단 로직 부정확

stack[0] 이 Kit 의 session anonymous spec (refs_count=0) 인 경우, 단순히 `stack[0].layer.identifier` 만 보면 LAM sublayer (stack[1]) 가 master USD spec (stack[2]) 보다 stronger 라는 사실을 놓치고 잘못된 WARN 출력.

### 변경 — `morph.lam_control/morph/lam_control/lam_runtime_evaluator.py`

#### 1. `LAM_FREEZE_MIN_SCALE = 1.0e-9` 클래스 상수 추가

`_set_prim_layer_offset` 진입 시 `abs(scale) < 1e-12` 인 입력은 자동으로 `1e-9` 로 변환:

```python

    scale = self.LAM_FREEZE_MIN_SCALE
    if not getattr(self, "_diag_freeze_scale_clamp_warned", False):
        self._diag_freeze_scale_clamp_warned = True
```

효과:
- `IsValid()=True` 라 USD 평가가 정상 처리됨.
- `inst_tc = freeze_tc + master_tc * 1e-9` 라서 master_tc 가 1e9 sec(약 31.7 년) 진행해도 inst_tc 변화는 1 sec 정도 → **시각적으로 freeze 와 동등**.
- 호출자(`_sync_layer_offset_mapping` 의 freeze 분기) 는 그대로 `scale=0.0` 으로 호출 — 의도 표현은 바뀌지 않음, 보정은 author 직전 1 곳에만.
