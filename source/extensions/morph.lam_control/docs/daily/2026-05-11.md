## 2. 사용자 ↔ AI 피드백 흐름 (의사결정 시간 순)

### 2.1 사용자 합의 Q

> "USD timeline 기반 playback 은 '전역 시간축' 구조이기 때문에 독립 animation
> playback 과 충돌한다. FBX 기반 USD 자산에는 baked timeSamples 가 포함될
> 가능성이 높기 때문에, 실제 production 환경에서는 **'Offscreen Animation Evaluation
> + Master Render Stage' 구조** 가 가장 안정적이고 현실적인 해결책이다."

**합의**: 그대로 옵션 E 진행.

### 2.2 사용자 요구 확장

> 사용자가 lam_control 의 목표 시나리오를 상세 기술. 핵심:
> - 여러 USD 를 별도 stage 에 로드 (각각 fbx→usd / 테스트 curve animation)
> - 단일 viewport 합성 (모든 자산을 한 viewport 에서 봄)
> - 시퀀스 편집기에서 stage 별 timeline 재생 / MOVE / ROTATE 등 step 생성
> - **하나의 JSON 으로 저장 / 로드**
> - 여러 JSON 이 **wall clock 시간축에서 중첩 실행** (event_1@1s 5s + event_2@3s
>   중첩 시 둘 다 끊김 없이 진행)
> - **한 step 안에서 여러 stage 의 timeline / MOVE / ROTATE 를 동시 트리거**

**합의 결과**:
- 위 모든 시나리오가 옵션 E 의 evaluator(=dispatcher) 모델 위에서 자연 동작.
- "stage 분리" = master stage 가 분리되는 게 아니라 **평가용 offscreen stage 가
  instance 마다 1 개씩 추가** 된다는 의미. master 는 항상 1 개 (viewport 합성 요구).
- 한 step 안 multi-target → step schema 의 `targets: [StepRef, ...]` 확장으로 표현
  가능. evaluator / runtime 변경 0.
- JSON 중첩 실행 → scheduler 의 **player pool** 도입으로 자연 동작. 각 player 가
  target instance 의 `virtual_time` 만 갱신하고 evaluator 는 매 frame 모든 runtime
  의 `evaluate_and_write` 호출 → last-writer-winner.
- 같은 instance 가 두 JSON 의 동시 target → **사용자 보장 영역** (그렇게 작성 안
  함). 시스템은 last-writer-winner + 진단 log 만 제공.

### 2.4 사용자 우려 2 — "USD 여러 개 로드하면 한 stage 에 합쳐지는데 stage 분리 계획이 깨진 거 아닌가?"

**해결**: 두 계층 분리 설명.

| 계층 | 현재 / B-2 후 |
|---|---|
| 사용자가 viewport 에서 보는 stage (Hydra) | **항상 1 개** (사용자 요구 "1 viewport 합성" 의 필수). |
| 평가용 stage (in-memory, 안 보임) | 지금 0 개 → B-2 후 **instance 마다 1 개씩** 추가. |

→ 사용자 합의: "아하 — B-2 가 진행되면 (평가용) stage 가 분리되는 거지" 로 정리.

### 2.5 사용자 우려 3 — "offscreen 이 안 보이면 사용자가 그 prim path 를 어떻게 알고 step 에 입력하나?"

**해결**: master ↔ offscreen 의 prim_path 매핑.

```
Master (보임)            Offscreen A (안 보임)
/World/aaa       ◄────►  defaultPrim (자산 root)
  ├─ Body       ◄────►    ├─ Body
  ├─ LeftArm    ◄────►    ├─ LeftArm
  └─ SkelRoot   ◄────►    └─ SkelRoot
```

- 사용자는 항상 **master 의 Stage 패널** 에서 prim path 복사.
- step 의 `prim_path` 필드는 master path 그대로.
- runtime 이 그 path 를 자산 내부 path 로 매핑 (offscreen 의 defaultPrim 산하 동일
  이름의 prim 을 자동 매칭).
- B-2-a 권장값이 정확히 이 워크플로우 보존을 위해 reference 를 master 에 그대로
  남기고 timeline 만 freeze 하는 설계.

→ 사용자 합의 후 B-2 진행 요청.

### Step 2. 옵션 E 핵심 검증 (단일 instance) — Phase B-3

1. USD 1 개 로드 (자산이 timeSamples 를 가져야 함 — curve animation 포함된 test1.usd 등).
2. 시퀀스 편집기 → USD_TIMELINE step 1 개 추가 (range=full, speed=1, loop=false).
3. RUN.
4. 콘솔에서 다음 로그 순서대로 확인:
   - `[LAM/L5] OPTION_E path enabled (Phase B-1) — hotfix 6-10 paths skipped` (1 회)
   - `[LAM/L5] OPTION_E freeze authored prim=/World/aaa offset=0 scale=1.0e-09` (1 회)
   - `[LAM/Runtime] init prim=/World/aaa offscreen_stage=anon:... source=...` (1 회)
   - `[LAM/Runtime] cache built prim=/World/aaa attrs=N` (N ≥ 1)
   - `[LAM/Runtime] update prim=/World/aaa virtual_time=X.XXXs timeCode=Y.YYY attrs=N wrote=N` (1 회)
5. viewport 에서 자산이 자기 timeline 으로 정상 재생되는지 확인.

진단 시그널:

| 로그 | 의미 / 대응 |
|---|---|
| `setup_offscreen_stage FAIL` | 자산 파일 경로 문제. source_asset 확인. |
| `cache built ... attrs=0` | 자산 prim 산하에 timeSamples 가 있는 attribute 가 없음. Skel-only 자산이면 Phase C 의 책임. |
| `evaluate ... wrote=0` (N>0 인데 wrote 0) | master mirror prim 의 같은 이름 attribute 매핑 실패. 매핑 정책 확인. |
| `OPTION_E freeze authored` 안 나옴 | master 의 reference 가 root layer 에 author 안 됨. multi_usd_loader 호출 flow 확인. |
| 화면이 정지 (재생 안 됨) | freeze 가 너무 강함 또는 default write 가 안 일어남. wrote 카운트 확인. |
| 화면이 핫픽스 10 처럼 동시재생 | 옵션 E 가 안 켜진 것. `get_use_option_e()` 호출로 True 확인. |

### Step 3. multi-instance 시각 검증 — Phase C-2

1. USD 2 개 로드 (예: test1.usd + test2.usd).
2. USD_TIMELINE step 으로 `aaa` 만 PLAY → 기대: `aaa` 만 timeline 진행, `aaa_1` 은 frozen (첫 frame).
3. 다시 `aaa_1` 도 PLAY → 기대: 둘 다 자기 timeline 으로 독립 진행, depth-aware 합성.

→ 핫픽스 6-10 시대의 동시재생 버그가 해소됐는지 확인하는 최종 step. 이게 통과되면 **옵션 E 의 핵심 약속 충족**.

### Step 4 (병렬 가능). A-3 — 사용자 추가 요구 구현

- step schema `targets: list[StepRef]` 확장 (단일 ref 도 호환).
- scheduler 의 **player pool** 도입 → 여러 JSON 동시 trigger 시 non-blocking.
- 외부 event runner 의 `trigger_json` 가 새 player 만 push 하고 즉시 리턴.
- UI 의 step 편집창에 multi-target row 추가/삭제 row.

→ Step 1~3 와 직교. 어느 시점에 시작해도 옵션 E 와 충돌 0.

## 12. B-3 3차 진단 — 자산 구조 식별 단계 (2026-05-11)

### 12.1 사용자 2차 보고 — `[Option E 진단]` 버튼 활용

> ```
> [LAM/L5] completed prim=/World/aaa (option_e) prev_t=1.996s new_t=2.000s dt=0.0090s sp=1.000 start_t=0.000s end_t=2.000s
> [LAM/L5] DUMP flag=True master_stage_ok=True root_layer=anon:...:World0.usd update_sub=set | prim=/World/aaa state=stopped vt=2.000s src='C:\\...\\lam\\usd\\test1.usd' freeze=yes runtime(set offscreen='C:\\...\\lam\\usd\\test1.usd' ready=True attrs_cached=0 last_wrote=0 last_vt=2.0)
> ```

핵심 단서 (완전히 분리됨):

| 신호 | 값 | 의미 |
|---|---|---|
| `flag` | True | Option E 경로 활성. |
| `master_stage_ok` | True | master stage 준비됨. |
| `update_sub` | set | update tick 정상 구독됨. |
| `prev_t/new_t/dt` | 1.996 → 2.000s, dt 0.009s | vt 진행 정상 (2 초 동안 60 fps). |
| `freeze` | yes | `_ensure_option_e_freeze` 정상 author. |
| `ready` | True | offscreen stage 정상 open. |
| **`attrs_cached`** | **0** | **`_build_attr_cache` 가 timeSamples attribute 를 한 개도 못 찾음.** |
| `last_wrote` | 0 | write 한 번도 안 일어남 → 화면 변화 없음. 당연. |

→ **가설 H2 적중**: cache build 가 0 건. evaluator 와 offscreen 인프라는 정상이고,
오로지 attribute 발견 단계만 실패.

### 12.2 cache build 가 0 일 수 있는 자산 구조

1. 자산 default prim 자체에는 timeSamples 가 없고, 자식 prim 에 분산된 경우 — 정상은 stack traverse 가 잡지만, master 측에 자식이 reference 합성으로 나타나지 않는 경우 매핑이 끊김.
2. 자산의 animation 이 default prim 의 sibling (다른 root prim) 에 있는 경우 — master 의 `/World/aaa` reference 는 default prim 만 가져옴 → sibling animation 손실.
3. 자산이 instanceable → 자식이 prototype 안에 있어 `GetChild` 가 가짜를 반환.
4. 자산의 animation 이 timeSamples 가 아닌 다른 형식 (예: pure curve API, anim layer 별도) — 본 단계의 cache 는 timeSamples 기반이므로 0 건.
5. FBX→USD 변환 후 animation 이 skel/anim 으로 export 되어 xform 에는 timeSamples 가 없는 경우 — Phase C (Skel) 가 필요.

### 12.3 적용한 진단 보강 (`lam_instance_runtime.py`)

| 항목 | 내용 |
|---|---|
| cache build 진입 로그 | `cache map off_root=<path>(<type>) -> master=<path>(<type>) master_children=[...]` — 매핑 시작 위치와 master 측 자식 목록을 한 번에 식별. |
| master 측 자식 매핑 실패 진단 | 자식들이 master 측에 없을 때 모아서 한 줄 `cache children NOT_FOUND_IN_MASTER ... names=[...]` 로 출력 (최대 20 개). |
| cache=0 시 fallback dump | `_diag_dump_offscreen_animatable()` — offscreen stage 전체 traverse 하며 **timeSamples 보유 attribute 의 path/sample 수를 최대 30 개 dump**. 자산의 어디에 animation 이 있는지 확정 식별. |

### 12.4 적용한 자동 fix — `OverridePrim` 으로 mirror 자식 자동 생성

master 측에 자식 prim 이 없을 때(케이스 1·2), 본 patch 에서는 `master_stage.OverridePrim(child_path)`
로 mirror 자식을 만들어 매핑을 이어간다.

- USD `OverridePrim` 은 root layer 의 `over` 정의로 prim 을 author — reference 안 prim 을
  외부에서 override 하는 표준 패턴. 자산 USD 파일은 일절 건드리지 않음.
- 이 후 자식의 attribute mirror 가 가능해져 cache 가 채워짐 → write 가 가능.
- `tbs_control_1` 영향 0 (lam_master_stage 의 self-owned master 만 수정).

## 13. FPS 30 단일 정책 — 단일 진입점 강제 (2026-05-11)

### 13.1 사용자 요구

> "FPS 는 무조건 30 으로 고정이 되어야 해. 즉 USD 타임라인에서 30 당 1 초가 소요되면 되는거야."

### 13.2 결정

- **단일 정책 상수** `LAM_FIXED_FPS: float = 30.0` (lam_types.py 모듈 레벨).
- `AnimationInstance.__post_init__` 에서 `asset_tps` 를 항상 `LAM_FIXED_FPS` 로 정규화. → 어떤 경로(loader / discovery / JSON 입력 / 직접 생성)로 인스턴스가 만들어져도 tps 는 항상 30.
- 자산 USD 의 헤더 `GetTimeCodesPerSecond()` 는 **진단 로그용**으로만 출력 (의사결정에 사용 X).
- 자산 frame range 의 의미: `frame N` 은 항상 `N/30` 초. 자산이 24/60 fps 로 export 되었어도 LAM 에서는 30 fps 기준으로 해석.

### 13.3 변경된 파일 (LAM only, `tbs_control_1` 영향 0)

| 파일 | 변경 |
|---|---|
| `lam_types.py` | 모듈 상수 `LAM_FIXED_FPS = 30.0` 신설. `AnimationInstance.__post_init__` 에서 `asset_tps = LAM_FIXED_FPS` 강제. |
| `lam_instance_runtime.py` | `evaluate_and_write` 의 `tps = LAM_FIXED_FPS`. offscreen stage 도 `SetTimeCodesPerSecond(30)` + `SetFramesPerSecond(30)` 으로 정규화 (자산 파일 비건드, in-memory stage 메타만). |
| `lam_runtime_evaluator.py` | `_start_time_seconds` / `_end_time_seconds` / `_sync_freeze_state` / `_set_animation_time` 의 tps 모두 `LAM_FIXED_FPS`. 진단 로그도 `tps=30(forced)` 로 표기. |
| `lam_sequence_engine.py` | `_estimate_usd_timeline_duration` / `_refresh_instance_asset_time_from_stage` / USD_TIMELINE 진단 로그 / `apply_world_space_offset_correction` 호출의 tps 모두 `LAM_FIXED_FPS`. |
| `lam_playback_scheduler.py` | `_range_start_seconds` / `range_end_seconds` 의 tps `LAM_FIXED_FPS`. |
| `lam_attribute_reauthor.py` | `tps = LAM_FIXED_FPS`. |
| `lam_offset_correction.py` | `apply_world_space_offset_correction` 의 `asset_tps` 키워드 인자는 deprecated — 호환 유지, 어떤 값을 전달해도 `LAM_FIXED_FPS` 가 사용된다. |
| `lam_multi_usd_loader.py` | `read_asset_time_range` 가 자산 헤더의 tps 가 30 외 값이면 진단 로그 1 줄 출력 후 **항상 30 을 반환**. |

### 13.4 자산 frame 의 실제 의미 (사용자 USD 검증 case)

사용자 자산 `test1.usd` 는 `asset_time=[0.0, 110.0]` (자산 헤더 tps 가 무엇이든 상관없음).
LAM 30 fps 정책에서 의미:

- 전체 길이 = `110/30 ≈ 3.667` 초.
- 시퀀스 step `start_frame=0 / end_frame=30` → `1.0` 초 재생.
- 시퀀스 step `start_frame=0 / end_frame=60` → `2.0` 초 재생 (사용자 2 차 보고와 일치 — `range=frames[0,60]` / `est_duration=2.000s`).

→ 시퀀스 step 의 frame 입력 값은 자산 헤더와 무관하게 사용자 의도대로 동작.

### 13.5 검증 액션 (앞 §12 와 동일 절차, 결과만 비교)

1. Kit App 재시작.
2. USD 1 개 (`test1.usd`) 로드 → `USD_TIMELINE` step 1 개 (예: `start_frame=0`, `end_frame=30`) → RUN.
3. 콘솔에서 다음 확인:
   - `[LAM/L1b] asset header tps=... ignored — using fixed 30.0 ...` (자산 헤더 tps 가 30 외이면 출력)
   - `[LAM/Runtime] init prim=/World/aaa offscreen_stage=... tps=30.0(forced=30.0) timeCode=[...]`
   - `[LAM/SEQ] step[0] USD_TIMELINE ... range=frames[0.0,30.0] ... est_duration=1.000s ... @30.0fps(forced)`
   - 1 초간 60 frame 진행 후 `[LAM/L5] completed ... dt≈0.016s` (정상 60 fps 진행 시).
4. 이전 dump 와 동일하게 `[Option E 진단]` 으로 `attrs_cached` / `last_wrote` 확인.

## 14. 하단 타임라인 fps 30 고정 + RUN 시 진단 강제 (2026-05-11)

### 14.1 사용자 보고 + 추가 요구

> 1. 하단 타임라인 창의 fps 가 60 으로 되어 있어. 그 부분도 전부 기본 설정이 30 으로
>    되어야 해.
> 2. 동일 로그 — `attrs_cached=0`, 새 진단(`init` / `cache map` / `diag dump`) 한 줄도
>    안 보임.

### 14.2 분석

A) **하단 타임라인 = `omni.timeline` 의 UI**. 표시 fps 는 stage 메타 + timeline iface 의
   target framerate 가 결정. 지금까지는 offscreen stage 의 메타만 30 으로 정규화했고,
   **master stage / omni.timeline 양쪽은 강제 안 했음.** 그래서 60 으로 표시.

B) 새 진단이 한 줄도 안 보이는 결정적 원인:
   - `_diag_first_call_logged` / `_diag_first_eval_logged` 는 runtime 객체에 살아남는
     1 회용 플래그.
   - `_attr_cache_built=True` 면 `_build_attr_cache` 가 다시 호출 안 됨 → `cache map` /
     `diag dump` 도 출력 안 됨.
   - 사용자가 RUN 을 두 번째로 했거나, Kit 재시작 없이 코드만 바꾼 케이스에서는 runtime
     이 그대로 살아 있어 새 진단 메서드의 1회 출력이 모두 skip 됨.

### 14.3 적용한 변경

| 항목 | 파일 | 내용 |
|---|---|---|
| `MasterStage.force_fixed_fps_30()` | `lam_master_stage.py` | master stage `SetTimeCodesPerSecond(30)` + `SetFramesPerSecond(30)` + `omni.timeline.get_timeline_interface().set_target_framerate(30)` + `set_time_codes_per_second(30)` (있을 때만) 모두 호출. 진단 1 줄 출력. |

## 16) 사용자 결정 — Option A (Bake OmniGraph → timeSamples) 구현 채택

### 16.1 결정 메시지

> "무조건 1번은 안되는거야. a를 구현해줘"

- **1번 (글로벌 timeline 공유)**: 다중 인스턴스 독립 재생 요구사항 위반 → 폐기 확정.
- **A. Bake OmniGraph → timeSamples**: 자산을 한 번 정적 timeSamples 로 변환해 Option E
  로 재생 가능하게 만든다 → 채택.

### 16.2 채택된 베이크 파이프라인 개요

신설: `lam_bake_omnigraph.py`
공개 API: `bake_prim_to_timesamples_async(master_stage, inst_prim_path, asset_path, ...)`

흐름:

1. master(default) context 에 이미 `[+ USD 추가]` 로 reference 된 인스턴스
   (예: `/World/aaa`) 를 입력으로 받음 — 이 위치에는 OmniGraph 런타임이 살아있어 평가
   가능.
2. master timeline 의 현재 시각·재생 상태를 저장.
3. warm-up tick (timeline → `s_frame/fps` 으로 이동 + `app.next_update_async()` x 3) 후
   capture target 재수집. OmniGraph push 로 새 attribute schema 가 만들어진 경우를 catch.
4. 매 frame 0..end_tc 에 대해 `timeline.set_current_time(t)` + `next_update_async()` x 3 →
   인스턴스 산하 prim 의 `xformOp:*` / `visibility` / `xformOpOrder` 를 capture.
5. 새 anonymous `Sdf.Layer` 에 자산을 reference 로 박은 root 를 만든 뒤, capture 결과를
   asset_root 산하 path 로 path 변환해 `OverridePrim` + `CreateAttribute` + `Set(value, tc)`
   로 author. `OmniGraph/PushGraph` 등은 `over { active = false }` 처리.
6. `out_layer.Export(<asset>_baked.usd)` 로 디스크 저장. 작성된 attribute 가 0 개면
   명시적으로 실패 반환 ("OmniGraph 가 평가되지 않았거나 capture 대상이 비어있습니다").
7. timeline 의 시각을 복원 (best-effort). 사용자 측 timeline 은 bake 동안 잠시 scrub
   되었다가 자동 복원.

### 16.3 LAM Window 통합

- 등록된 인스턴스 행마다 `[Bake]` 버튼 추가 (`Remove` 옆).
- 클릭 시:
  1. 인스턴스의 `source_asset` 절대 경로 해석 (`master_path` 기준 상대 경로도 지원).
  2. `bake_prim_to_timesamples_async` 를 `asyncio.ensure_future` 로 스케줄.
  3. 진행률 콜백 → 하단 Log 라벨에 `Bake 진행 XX% (cur/total) ...` 표시.
  4. 성공 시: `MultiUsdLoader.remove_usd(inst.prim_path)` → `add_usd(source_asset=baked.usd,
     requested_id=inst.instance_id)` 로 자동 교체. 사용자는 그 다음 `USD_TIMELINE` step 을
     **Run** 하면 Option E 가 정상 동작 (timeSamples 가 있으므로 offscreen 평가 OK).

### 16.4 TBS 영향

- `lam_bake_omnigraph.py` 는 `morph.tbs_control_1` 의 어떤 심볼도 import 하지 않는다.

| 케이스 | 단서 | 다음 액션 |
|---|---|---|
| `targets=0` (warm-up 후에도) | 자산에 xformOp 자체가 없음 (e.g., `xformOp:transform` 도 없는 mesh 만의 자산) | 자산이 PushGraph 가 아닌 다른 메커니즘으로 변환됨 — 자산 검수 필요. |
| `targets>0` 인데 `attrs_written=0` | timeline scrub 으로 OmniGraph 가 push 를 안 함 (tick mode) | F-4 분기: Hydra Δ를 sampling 하는 별도 경로 검토. |
| `attrs_written>0` 이지만 viewport 상 정지 | baked.usd 의 timeSamples 가 모두 동일 값 (변화 없음). master 의 OmniGraph 가 이전에 한 번도 평가되지 않은 상태일 수 있음 | bake 전에 한 번 timeline 을 play→stop 해 OmniGraph evaluator 워밍업 후 재시도. |

### 16.6.1 1차 실사용 피드백 — 옆으로 누움 + 재생 안됨

**실측 로그 요약 (사용자, bake 직후 RUN):**

```
[LAM/Bake] done out=...test1_baked.usd frames=111 prims=2151 attrs_written=419881
            deactivated=['/Root/PushGraph'] elapsed=39.087s
[LAM/L1b] add_usd OK prim=/World/aaa src=...test1_baked.usd time=[0.0,110.0]@30.0fps
            upAxis_fix=Y->Z RotateX(+90)
...
[LAM/L5] OPTION_E first evaluate prim=/World/aaa state=playing vt=0.008s
            offscreen_asset='...test1.usd'        ← ❌ 옛 자산!
[LAM/Runtime] diag dump offscreen prim=/World/aaa animatable_attr_count=0
[LAM/Runtime] evaluate WARN no attr samples and Skel write failed
```

→ 두 가지 별개의 버그가 동시에 드러났다.

#### 버그 A — 자산이 옆으로 누움 (이중 RotateX)

원인 흐름:

1. `add_usd(test1.usd)` 시 master upAxis=Z, asset upAxis=Y → 차이가 있어 `/World/aaa` prim 에
   `xformOp:rotateX:upAxisFix = 90.0` 와 `xformOpOrder = [..., "xformOp:rotateX:upAxisFix"]`
   가 author 된다.
2. bake 가 `Usd.PrimRange(inst_prim)` 으로 `/World/aaa` 자신을 포함해 capture → 위 upAxis fix
   xformOp 가 baked.usd 의 `/Root` 에 함께 박힘.
3. baked.usd 의 stage upAxis 메타가 미설정(=USD 기본 'Y') 상태로 디스크에 저장됨.
4. `add_usd(test1_baked.usd)` 가 다시 호출되면 master(Z) vs baked.usd(Y) 가 또 다르다고
   판단해 `/World/aaa` 에 또 RotateX(+90) 을 author.
5. baked.usd 내부의 `/Root` 에 박힌 upAxis fix(첫 번째) + master 가 `/World/aaa` 에 박은
   upAxis fix(두 번째) → 이중 회전 → 90° 옆으로 누움.

**픽스:**

- 신설 `_read_asset_up_axis(asset_path)` — 원본 자산의 `UsdGeom.GetStageUpAxis` 를 읽는다.
- bake 시 `UsdGeom.SetStageUpAxis(out_stage, src_axis)` 로 baked.usd 의 stage upAxis 를 원본과
  동일하게 박는다 → re-add_usd 시 master 의 보정이 원본 자산을 직접 로드할 때와 *정확히 같은
  횟수* 만 적용된다.
- `_collect_targets()` 와 OmniGraph deactivate 수집에서 `inst_prim` 자신은 제외 (inst_prim 의
  `xformOp:*:upAxisFix` 같은 master 측 보정 op 가 baked.usd 에 새지 않게).

#### 버그 B — Option E 가 옛 자산을 계속 평가

원인:

- `_on_bake_instance` 에서 `loader.remove_usd(prim) → loader.add_usd(baked.usd, requested_id)`
  를 호출했지만, registry 의 `_notify` listener 는 `evaluator.invalidate_attr_cache(None)` /
  `invalidate_mapping(None)` 만 수행한다.
- evaluator 의 `_runtime_by_path[prim_path]` 에 들어있는 `AnimationInstanceRuntime` 인스턴스는
  **dispose 되지 않으며**, 그 `offscreen_asset` (옛 test1.usd) 캐시를 그대로 사용한다.
- 새 add_usd 가 prim customData 에 `lam:source_asset = baked.usd` 를 박았지만, 옛 runtime 이
  먼저 hit 되어 새 자산이 사용되지 않는다.

**픽스:**

- `_on_bake_instance` 가 `remove_usd → evaluator.forget_instance(prim_path) → add_usd` 순서로
  호출하도록 변경. `forget_instance` 는 이미 evaluator 가 가진 메서드로, `_runtime_by_path` 에서
  pop 하고 `dispose()` 까지 호출한다 → 다음 update tick 에서 새 runtime 이 baked.usd 로 init.
- 동일 누수가 일반 `[Remove]` / `[모두 초기화]` 에도 있어, `_on_remove` 와 `_on_reset_all` 도
  같은 패턴으로 보강.

### 16.6.2 사용자 측 재검증 절차

1. Kit App 재시작 (이전 turn 의 baked.usd 파일은 그대로 두고 새로 bake 권장 — 이전
   파일에는 upAxis 메타가 잘못 박혀있다).
2. LAM Window → `[모두 초기화]` → `[+ USD 추가]` 로 `test1.usd` 등록.
3. 인스턴스 행 `[Bake]` 클릭 → 콘솔에서:
   - `[LAM/Bake] done out=...test1_baked.usd ... attrs_written=K` (K > 0)
   - `[LAM/L1b] add_usd OK prim=/World/aaa src=...test1_baked.usd ... upAxis_fix=Y->Z
     RotateX(+90)` — RotateX 메시지 자체는 정상 (자산이 Y-up 이고 master 가 Z-up 이라면
     이게 정상 한 번 보정).
4. 시퀀스 `USD_TIMELINE step [0, 60]` → **Run** → 콘솔에서:
   - `[LAM/L5] OPTION_E first evaluate prim=/World/aaa state=playing vt=...
     offscreen_asset='...test1_baked.usd'` ← **baked.usd** 가 맞아야 한다.
   - `[LAM/Runtime] cache built prim=/World/aaa attrs=K` (K > 0)
   - `[LAM/Runtime] update prim=/World/aaa virtual_time=... attrs=K wrote=K`
5. 화면에서 인스턴스가 정상 자세로 보이고, `Run` 시 timeline 이 독립 재생되어야 한다.

### 16.6.3 2차 실사용 피드백 — 끊김 / 느린 bake / 재사용

**실측 (사용자, 픽스 후 RUN):**

- bake 시간 = 40.66s (110 frame, prims=2150)
- 재생 dt = 0.067~0.078s ≈ 12~15 FPS (≪ 30 FPS 목표) → 끊기는 느낌.
- 매 RUN 로그: `attrs=3652 wrote=3652` — write 부하가 매 tick.

#### 문제 1 — 끊김 (write 부하)

원인: 자산 prim 2150 개 중 **실제로 움직이는 prim 은 일부**인데, bake 가 모든 xformOp 를
timeSamples 로 박아 evaluator 의 `attr_cache` 가 3652 attribute 를 매 tick write 함. 이 중
대부분이 정적인 mesh transform (transform 이 frame 마다 동일).

**픽스 (`lam_bake_omnigraph.py`):**

bake 출력 시 정적 attribute pruning 추가. 각 attribute 에 대해 모든 frame 의 value 가
`==` 인 경우 → `default` 1 개로만 author, timeSamples 는 박지 않는다. evaluator 의
`_build_attr_cache` 는 이미 `GetNumTimeSamples() <= 0` 인 attribute 를 cache 에서 제외하므로
(`lam_instance_runtime.py:804`), 정적 prim 의 write 부하가 자동으로 사라진다.

기대 효과: `attrs=3652 wrote=3652` 가 실제 움직이는 prim 의 attribute 수로 줄어듦 (자산에
따라 10~30 % 수준 예상) → dt ≪ 30 ms 로 안정 → 부드러운 재생.

#### 문제 2 — 느린 bake (40s)

원인: 매 frame `next_update_async()` x 3 + warm-up x 3 → 한 frame 당 3 tick.

**픽스 (`lam_bake_omnigraph.py`):**

PushGraph 는 stage 시각 변경 즉시 평가되므로 매 frame `next_update_async()` x **1** 로 충분.
warm-up 은 schema 안정용으로 x 2 만 유지. 110 frame 기준 ~ 35 % 시간 단축 예상.

#### 문제 3 — baked.usd 재사용

**현재도 가능**: 사용자가 `[+ USD 추가]` 로 `test1_baked.usd` 를 직접 선택해 로드하면 그대로
사용 가능. 단, 사용자의 워크플로우를 단순화하기 위해:

**픽스 (`lam_window.py` `_on_bake_instance`):**

1. 인스턴스 source 가 이미 `*_baked.usd` 이면 안내 메시지 후 종료 (이중 bake 방지).
2. `out_path = <asset>_baked.usd` 가 이미 존재하고 `mtime(baked) >= mtime(원본)` 이면
   bake 자체를 생략하고 곧장 인스턴스 교체로 진입 (skip 캐시).
3. 강제 재bake 가 필요한 경우 사용자는 baked.usd 파일을 직접 삭제 후 [Bake] 재클릭.

UI/UX 흐름:

- 1차 [Bake]: 39 s, baked.usd 생성, 교체.
- 2차 이상 [Bake]: 즉시 ("Bake 생략(캐시) — 이미 최신 baked.usd 존재") + 교체만 0.x s.
- 다음 세션: `[+ USD 추가]` 로 `test1_baked.usd` 를 그대로 선택해도 OK (사용자 자유).

### 16.6.4 사용자 측 재검증

1. **이전에 만든 `test1_baked.usd` 는 정적 pruning 이 안 된 버전이므로 삭제 권장.**
2. Kit 재시작 → LAM Window → `[모두 초기화]` → `[+ USD 추가]` 로 `test1.usd` 등록.
3. `[Bake]` 클릭. 콘솔에서:
   - `[LAM/Bake] done out=...test1_baked.usd frames=111 prims=2150 attrs_written=K
     static_pruned=P deactivated=['/Root/PushGraph'] elapsed=XXs`
   - 기대: `elapsed` 가 이전(40.66s) 대비 ~25~30 s 수준으로 단축.
   - 기대: `static_pruned` 가 `attrs_written` 의 큰 비중 (예: 90%+) — 거의 대부분의 mesh
     transform 이 정적.
4. 시퀀스 `USD_TIMELINE [0, 60]` step → **Run** 후 콘솔:
   - `[LAM/Runtime] cache built prim=/World/aaa attrs=K` — **K 가 3652 → 수백 미만으로
     감소** 해야 한다.
   - `[LAM/Runtime] update ... attrs=K wrote=K` 도 비례 감소.
   - viewport 에서 끊김 없이 부드럽게 재생.
5. 2 번째로 `[Bake]` 를 누르면:
   - `Bake 생략(캐시) — 이미 최신 baked.usd 존재: ...test1_baked.usd` + 즉시 교체.
6. 다음 세션에서 직접 `[+ USD 추가]` → `test1_baked.usd` 선택해도 곧바로 Option E 로
   독립 재생 가능.
